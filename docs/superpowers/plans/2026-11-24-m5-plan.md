# M5: Storefront Extension Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Tasks in the same wave (see "Parallel build waves") own disjoint files and can be built by separate agents at the same time.

**Goal:** A shopper on any page of a store that enabled the AskCart app embed sees a launcher. Clicking it opens a chat that streams answers from `POST /api/chat`, shows product cards with Add to cart, and keeps going across page loads. On product pages, the merchant can also place an "Ask about this product" button and an FAQ block.

**Scope (phase 1 plan, M5 row):** app embed plus Shadow DOM widget, cards, add to cart, persistence, feedback, i18n and a11y, plus the FAQ block and the "Ask about this product" block. It also writes the `AppInstallation` metafield that carries the widget config (phase 1 plan, Task 4 note: "Write the `AppInstallation` metafield in M5, when the widget config exists"). It carries D7, D30, D32, D36, D39, D72, D75, D81, D83, D84 and D85, and UD1–UD18.

**Out of scope (later milestones):**
- the Settings page, its live preview (UD20) and the contrast warning in Settings (UD17), plus the FAQ editor and the "Enable widget" deep link (all M7). M5 makes the widget mountable with a plain config object, so M7's preview can reuse it (see Task 30),
- FAQ text in retrieval (chunks), and suggestions built from thumbs-down (M7/M8),
- rate limits, Turnstile, the monthly cap and the retention job (M10). The notice states the retention period now, but the deletion job comes in M10,
- the `DELETE /api/chat/conversation` backend (D84). **Another agent is building it in parallel** as `DELETE /api/chat/conversation?shop=…` with the `X-Conversation-Token` header. This plan treats it as done and builds the widget UI only.

**Architecture (one page view, then one chat):**
1. **Page load, no call to our server (§8b point 1).** The app embed's Liquid reads the widget config from the app-data metafield `app.metafields.askcart.widget` and the page context (shop, locale, country, currency, product, cart routes, privacy link). It writes both into data attributes and renders nothing else. The launcher script (about 2 kB, loaded `async` by the block schema) draws the launcher in a Shadow DOM and, if turned on, the teaser.
2. **First click.** The launcher loads `askcart-widget.js` (C20 decides where it is hosted) and calls `AskCart.open()`.
3. **Chat.** The widget restores history with the stored token (UD13), then sends `POST /api/chat` with a fresh `requestId` per message (D81). It reads the SSE stream with `fetch` + `ReadableStream` (`EventSource` can't send a POST body) and renders text as text only (§7.7). Cards are grouped after the answer (UD12).
4. **Add to cart.** The widget calls the storefront's own `/cart/add.js` with the numeric variant id (D30), shows "Added · View cart", dispatches `cart:updated` (UD11), and logs the add to our server for UD21 and UD22 (§7.6, "The event is logged for analytics").
5. **Thumbs, New chat, Clear chat.** These go to small token-authorised endpoints.

**Tech Stack:** as M4, plus the widget. D39 settles the framework: **vanilla JS in a Shadow DOM**, no UI framework. It's written in TypeScript and bundled with esbuild into the extension's assets. Unit tests run in Vitest with a DOM environment (happy-dom). Both new tools are dev-only and pending **C29**. Shopify CLI 5.0.2.

**Spec:** `product.md` §7.6 (SSE events, add to cart), §7.7 (widget, FAQ block, rendering safety), §7.10, §7.13 (`Faq`), §8, and D7, D30, D32, D36, D39, D41, D72, D75, D81, D83, D84, D85, D87. `ui-ux.md` UD1–UD18, plus UD20 and UD21–UD22 for the data M7 will need. This plan continues the task numbers from `2026-11-24-m4-plan.md` (Tasks 13–21) and the decision numbers from its C11–C19. The earlier plans' Global Constraints still apply.

## Research notes (checked 2026-11-24)

The shopify-ai-toolkit plugin wasn't available in this session, so everything below comes from shopify.dev pages fetched directly. Items marked **verify** get a task step on the dev store before any code relies on them.

**Theme app extensions** ([configuration](https://shopify.dev/docs/apps/build/online-store/theme-app-extensions/configuration), [build](https://shopify.dev/docs/apps/build/online-store/theme-app-extensions/build))
- **Layout:** `extensions/<name>/` with `assets/`, `blocks/`, `snippets/`, `locales/` and `shopify.extension.toml` (`type = "theme"`). It's generated by `shopify app generate extension`, choosing "Theme app extension".
- **Enforced limits:**
  - 10 MB for all files,
  - 30 blocks,
  - 100 KB of Liquid across all files,
  - 100 locale files of up to 15 KB each.
- **Suggested limits:** JS referenced by a block schema up to **10 KB compressed**, and CSS up to 100 KB compressed.
- **App embed blocks:** target `head`, `compliance_head` or `body`. A schema `javascript` file is loaded as `<script async>` in `<head>`, once per page even when several blocks reference it. Assets are served from Shopify's CDN, and `{{ 'x.js' | asset_url }}` gives their URL.
- **Liquid scope:** app embed blocks see "only the Global Liquid scope for the page they render on". App blocks see `block` and the section's `id` only. The page doesn't list `product`, `request` or `localization` explicitly, so **verify** in Task 23 that `product`, `request.locale`, `localization.country` and `cart` render inside our embed and block.
- **`shopify app dev`:**
  - builds and hot-reloads the extension,
  - uses `--theme <id|name>` to choose the host theme (otherwise it uploads Dawn),
  - previews in Chrome only.

  App embeds are switched on by the merchant in the theme editor.
- **Releases:** `shopify app deploy` creates a version and releases it, and stores can take several minutes to pick it up. `--no-release` then `release` splits the two.

**App-data metafield** ([store settings in app-owned metafields](https://shopify.dev/docs/apps/build/security/storefront/store-settings-in-app-owned-metafields), [Liquid `app` object](https://shopify.dev/docs/api/liquid/objects/app))
- **Write:** `currentAppInstallation { id }`, then `metafieldsSet` with that `ownerId`. §7.2 says no write scope is needed. **Verify** in Task 24, because the page doesn't list scopes.
- **Read in Liquid:** `app.metafields.<namespace>.<key>`, through the `app` object, which is meant for theme app extensions.
- **The config is not secret.** "Liquid can read any metafield regardless of its storefront access setting": anyone can view the page source, so it must never hold a secret.
- **A common pitfall** reported on the community forum: an empty value when the token used to write belongs to a different app than the extension. Our extension and our offline token belong to the same app.

**Cart** ([Ajax Cart API](https://shopify.dev/docs/api/ajax/reference/cart), [storefront actions](https://shopify.dev/docs/api/storefront-events-and-actions/actions/call))
- **`POST {root}cart/add.js`:** `{ items: [{ id: <numeric variant id>, quantity }] }`. Use locale-aware URLs (`window.Shopify.routes.root`, or Liquid `routes.cart_add_url`).
- **Errors:**
  - **422** "Cart Error" for sold out, "You can't add more…" (the quantity is capped), or "Cannot find variant",
  - **429** after repeated failed adds, so back off.
- **Refreshing the theme's cart:** an optional `sections` parameter can re-render up to 5 sections in the same call. That's theme-specific, so UD11 leaves it out.
- **New since UD11 was decided: Shopify's standard storefront actions.**
  - The call is `await Shopify.actions.updateCart({ lines: [{ merchandiseId: 'gid://shopify/ProductVariant/123', quantity: 1 }] })`.
  - It refreshes the theme's cart in place on themes it recognises, including Horizon- and Dawn-based ones.
  - **On a theme it doesn't recognise, it falls back to a full page reload.**
  - Actions are ready only after `DOMContentLoaded`, and `updateCart.isDefault()` says whether the theme configured its own handler.
  - Themes then fire standard events such as `shopify:cart:lines-update` ([standard events](https://shopify.dev/docs/storefronts/themes/best-practices/standard-events.md)).
  - This is raised as **C21**.

**Locale and country in Liquid** ([request](https://shopify.dev/docs/api/liquid/objects/request), [localization](https://shopify.dev/docs/api/liquid/objects/localization))
- `request.locale` is a `shop_locale`, so use `request.locale.iso_code`.
- `localization.country` is "the currently selected country on the storefront", so use `.iso_code` (ISO 3166-1 alpha-2).
- `request.page_type == 'product'` tells us we're on a product page.
- `request.design_mode` is true inside the theme editor.
- The pages don't show `iso_code` examples, so **verify** in Task 23.

**Calling our backend: direct CORS, not an App Proxy** ([app proxies](https://shopify.dev/docs/apps/build/online-store/app-proxies))
- **Keep direct CORS** (M4 already allows exactly the store's domains, `src/lib/chat/cors.ts`). Product.md §6 says "There's no app proxy".
- Why not a proxy:
  - Shopify's docs say nothing about streaming through an App Proxy,
  - community reports describe SSE being held until the response ends ([thread](https://community.shopify.com/t/how-can-shopify-app-proxy-be-configured-to-allow-sse/295440)),
  - a proxy strips cookies, which we don't use anyway.
- A proxy would only matter for recognising logged-in customers, which is phase 2 (D82).
- **Ceiling:** origins that aren't in `stores.domains` are refused. That includes `*.shopifypreview.com` share links and our own app domain (M7's preview). Both are listed in the failure modes.

**Next.js 16.4.6:** the new route handlers follow M4's notes: `OPTIONS` defined for the preflight, no `runtime` export (cacheComponents), and `Cache-Control` set by hand on GETs. Re-read `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/route.md` before Task 27/28.

## Shared contract (written in Task 23, used by everyone)

`src/lib/widget-contract.ts` holds types only, and both the server and the widget import it. esbuild strips types, so nothing from the server ends up in the bundle.

```ts
export type WidgetConfig = {          // the metafield value, written by Task 24, read by Liquid and the widget
  v: 1;
  enabled: boolean;
  apiBase: string;                    // https origin of our app, e.g. the tunnel in dev
  name: string;                       // header title, merchant text (UD7)
  accent: string;                     // #rrggbb
  avatarUrl: string | null;           // https://cdn.shopify.com/... only (UD7b)
  launcher: { style: "pill" | "icon"; label: string | null; side: "right" | "left"; offset: number }; // UD1, UD2
  welcome: string | null;
  suggested: string[];                // at most 4
  teaser: { enabled: boolean; text: string | null; delaySec: number };  // UD6
  stockThreshold: number;             // UD10, the same value the server uses
  retentionDays: 30 | 90 | 365;       // UD16 notice (D41)
};
export type PageContext = {           // from Liquid, per page view
  shop: string; locale: string; country: string | null; currency: string | null;
  productId: string | null; cartAddUrl: string; cartUrl: string; privacyUrl: string | null; designMode: boolean;
};
export type Card = import("./chat/turn").Card;   // re-export; the SSE `product` payload
export type DoneEvent = { conversationToken: string; messageId: string | null };   // messageId added in Task 22
export type HistoryItem = { id: string; role: "user" | "assistant"; content: string; status: "ok" | "cut_off";
                            cards: Card[]; rating: -1 | 1 | null };
// Widget-internal seams so Wave 3 tasks don't touch each other's files:
export type CardsRenderer = (into: HTMLElement, cards: Card[], ctx: WidgetCtx) => void;          // Task 31
export type FeedbackRenderer = (into: HTMLElement, messageId: string, rating: -1 | 1 | null, ctx: WidgetCtx) => void; // Task 32
```

`WidgetCtx` carries `config`, `page`, `api` (from Task 25), `t` (i18n) and `announce(text)` (the aria-live helper).

## Global Constraints (M5 additions)

- **No server call on page view.** Until the shopper clicks, nothing reaches our server. The exception is a reopened panel (UD13), which only happens after the shopper used the chat.
- **No secrets in Liquid or the metafield.** The config is public.
- **Text only.** No `innerHTML` with any string from the model, the merchant or the server. Build nodes with `createElement` and `textContent`. Task 33 adds a lint check that `innerHTML` doesn't appear in `widget/src`, except for one static SVG icon module.
- **Only allowed URLs.** `https:` links only, and `cdn.shopify.com` images only. `apiBase` must be `https:`.
- **Our own CSS only.** Everything lives in the shadow root. Use `px`, never `rem`, because themes set `html { font-size: 62.5% }`. The font is inherited (UD7). One host element at the end of `<body>`, with `z-index: 2147483000`.
- **Size budget.** The launcher is at most **4 kB gzip** (the schema-loaded script limit is a suggested 10 kB). The chat bundle aims for at most **30 kB gzip**. Task 33 checks both.
- **Privacy.** `pageUrl` is sent as `origin + pathname` only, with no query string (UTM and email parameters stay out). Tokens are never put in URLs.
- **Storage can fail.** localStorage can throw (blocked storage, private modes). Every access is wrapped, and the widget falls back to memory only: the chat works but doesn't persist.
- **One owner per file.** New migrations are created only in Task 22, and `package.json` and `.gitignore` are changed only in Task 23. A later need for either goes back through those tasks' owners or waits until Task 33.
- **D49 items** (notice wording, label texts, card design) are Claude's drafts until the user approves them before the beta.

## Review Focus

1. **A product description or answer containing `<img src=x onerror=…>` or `javascript:` links** renders as plain text, and no attacker URL becomes a link or image. Tests in Tasks 30 and 31.
2. **A merchant welcome text containing `"></div><script>`** can't break out of the Liquid data attribute. Test in Task 23 (Liquid escaping) and Task 24 (config validation).
3. **The conversation token** never appears in a URL, and is sent only to `apiBase` in the `X-Conversation-Token` header or the JSON body. It's stored under a per-shop key. Tests in Task 25.
4. **Thumbs and cart-event endpoints:** a token for conversation A can't rate or log against a message of conversation B or of another store. Tests in Task 27.
5. **A dropped SSE stream** leads to one retry with the same `requestId`. The partial bubble is replaced by the replayed answer, never answered twice and never duplicated on screen. Test in Task 30.
6. **Add to cart** sends the numeric variant id and never adds a disabled (sold-out) variant. A 422 shows the store's message, translated where we can. Test in Task 31.
7. **Theme isolation:** a theme stylesheet with `* { color: red !important }`, `button { all: unset }` and `html { font-size: 10px }` doesn't change the widget's layout. Checked in Task 33.

## Open decisions (PENDING)

Nothing that depends on a pending choice is built until the user decides. Each task above names the choice it waits on. Where a task needs a default to keep moving, it builds the recommended option behind one constant and says so.

- **C20 Where the chat script is hosted.** D39 says the chat script loads "from our domain". The extension can also ship it on Shopify's own content network.
  - (a) Shopify's network, packed with the extension: fast everywhere, no load on our server, but every widget fix needs an app release (a few minutes to reach stores),
  - (b) our server, as D39 says: fixes go live instantly, but our server serves the script to every shopper who opens the chat, and in development the address changes with each tunnel.
  - **Recommended: (a).** It keeps page views and chat openings off our server (§8b) and matches how Shopify expects theme extensions to ship code. It changes D39's wording, so it needs your OK.
- **C21 How "Add to cart" updates the store's own cart icon.** UD11 chose a plain add with no theme-specific code, so the cart icon may stay stale until the next page. Shopify now offers a standard "update cart" action that refreshes the cart icon on Dawn- and Horizon-style themes, but **reloads the whole page** on themes it doesn't recognise.
  - (a) keep UD11: a plain add, "Added · View cart", and the stale icon,
  - (b) always use Shopify's action: the icon updates on common themes, but some shoppers get a page reload mid-chat (the chat reopens with history, but the moment is jarring),
  - (c) a plain add first, and use Shopify's action only on themes that have set it up themselves (no reload risk), otherwise as (a).
  - **Recommended: (c).** It never reloads the page, and it improves the icon where the theme supports it. Task 33 records what Dawn and Horizon do, so we can revisit.
- **C22 "New chat" and "Clear chat".** UD13 has a "New chat" button that only forgets the chat in this browser. D84 adds "Clear chat", which deletes it from our server.
  - (a) two items in the chat menu: "New chat" (the merchant still sees the old chat in reports) and "Delete chat" (gone for good),
  - (b) one button that always deletes and starts fresh,
  - (c) one "New chat" button only, and deletion only through the store's privacy contact.
  - **Recommended: (a).** Shoppers who just want to start over don't erase the merchant's insight, and shoppers who care about privacy can delete.
- **C23 Where merchants change the widget's look before the Settings page exists (M7).**
  - (a) only in our Settings page (M7); until then the widget uses the defaults, and in development we set them by hand,
  - (b) also add a few options (side, colour) in Shopify's theme editor, which means two places to edit the same thing.
  - **Recommended: (a).** One place to edit, as D39 says, and no confusion about which setting wins.
- **C24 FAQ content before the FAQ editor exists (M7).** M5 builds the FAQ block and its table, but the editor comes in M7.
  - (a) during M5, FAQs are added only with a developer script on the dev store,
  - (b) pull the FAQ editor forward into M5.
  - **Recommended: (a).** The editor belongs with the other dashboard pages, and the block can be fully tested with seeded FAQs.
- **C25 What "Ask about this product" does.**
  - (a) opens the chat with that product as context, and shows that product's FAQ questions as one-tap suggestions,
  - (b) also sends "Tell me about <product>" automatically, so an answer starts straight away.
  - **Recommended: (a).** The shopper stays in control, and no message is spent (each counts toward the 1,000-message cap) unless they ask.
- **C26 Prices on cards when the shopper sees the store in another currency.** Cards show the store's main-currency price (M4), but a shopper browsing in euros sees euro prices elsewhere on the store.
  - (a) show the main-currency price anyway,
  - (b) hide the price on the card in that case, with "See price on the product page", and keep Add to cart (checkout charges the right local price),
  - (c) fetch the local price for the shopper's country in the same Shopify request (a small M4 change, measured for cost first).
  - **Recommended: (c),** with (b) as the widget's safety net until (c) ships. Shoppers see the price they'll actually pay, and never a confusing mix.
- **C27 Changing a thumbs rating.**
  - (a) a shopper can change or remove it at any time,
  - (b) the first tap is final.
  - **Recommended: (a).** Mis-taps happen, especially on phones, and the merchant's report should reflect what the shopper really thinks.
- **C28 How often the teaser line appears** (when the merchant turns it on).
  - (a) once per visit, and never again once the shopper has opened the chat or closed the teaser,
  - (b) on every page, after the delay.
  - **Recommended: (a).** It invites without nagging, and it doesn't cover the page on every click.
- **C29 Two developer tools for building the widget** (nothing ships to shoppers or merchants): esbuild to pack the widget into one small file, and happy-dom to test it without a browser.
  - (a) add both,
  - (b) hand-write the widget as one plain JavaScript file with no build step, tested only by hand.
  - **Recommended: (a).** They're the smallest standard tools for this, and they let most of the widget be tested automatically.
